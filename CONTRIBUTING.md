# Contributing to Bitwise

Thank you for your interest in contributing to this project! I'm glad you're looking to help out, but before you jump in, please take a read through these guidelines so we're all on the same page.

## How can I contribute?

There are tons of ways in which you can contribute. Some big ones are:

- Looking at open issues and seeing if there's any feature requests you can implement
- Coming up with features you'd like to see and opening issues requesting them... or implementing them yourself!
- Writing improved tests, especially for code in the as-yet untested packages such as `net.moctave.bitwise.ui`
- Improving documentation to make the app easier to use and the code easier to understand

## What should I do when I post an issue?

Before you post an issue, check to make sure no one else has posted a similar issue before. Then, create a new issue for each bug report or feature request you have, using the templates provided. Fill in the template to the best of your ability: the more detailed your bug report is, the easier it will be to fix the bug, and the more detailed your feature request is, the more likely I am to want to include it.

Once you've posted an issue, you may receive requests for clarification from me but you are not otherwise expected to do anything to address it. If you believe you're able to write the code to close an issue, you are free to do so and open a pull request with your changes.

If you believe your issue has been resolved, you may close it. If I close your issue and you feel it has not been resolved, please let me know.

## What should I expect when I open a pull request?

Pull requests (aka PRs) are the primary way to contribute to Bitwise. When you open a pull request, you will come face to face with a form asking you a few questions (Have you read this document? What does your PR do? Have you tested it?). Fill out the form and submit, and I'll get around to reviewing your PR when I have time - hopefully within a few days after you submit it.

Chances are, I'll have more questions and suggestions when I review your PR. This is totally normal. Once these are addressed, I will merge your PR and your code will become part of the main version of Bitwise!

## Are there any guidelines I need to follow when writing code?

Yes. This project has pretty thorough style rules, which you can find in the annotated [checkstyle file](checkstyle.xml). All your contributions are expected to follow this style guide, although the styleguide will not be enforced for tests.

Additionally, I have a couple of other policies:
- Write tests for any new code you write, and make sure to keep test coverage at or above either 90% or whatever it was before you touched it for every file you modify.
- Do not use AI coding tools. See the AI policies section for more details.
- When in doubt, contribute many small changes rather than one big one. Small changes are easier to test and debug and are more likely to get accepted faster.
- If you have questions, ask me! I'm generally available on GitHub and I occasionally even check [my email](moctave31415@gmail.com).
- **By contributing code, documentation, or any other hard changes to this program, you agree to be bound by the terms of the [AGPL v3.0 license](LICENSE). You acknowledge that your work may be added to, modified, or removed as a result of future contributions by others, without or without your knowledge and/or consent.**

## What are your policies on generative AI?

**AI generated code or content is forbidden in Bitwise.** This includes all code or documentation generated by LLMs such as chatbots or dedicated AI tools such as Copilot or Claude Code, and all images generated using AI models such as stable diffusion. **Please do not intentionally commit or PR any material generated in whole or part by AI.**

However, there are a few ways in which it may be acceptable to use AI to contribute. It is acceptable to use AI tools to:
- Summarize documentation for you
- Help you understand the codebase
- Explain programming concepts to you that you then use in *your own* code

In general, I don't have a problem with you using AI to help you contribute, but I draw the line at AI actually doing the work for you.

### Your AI policies are unenlightened garbage and why can't I just vibe code and get this project done faster?

1. Ethics. LLMs require mass copyright infringement to function properly. I'd rather not have someone else's code fragments in my repository.
2. Licensing. Sure, it's very unlikely that anyone's actually going to lose a court case for "writing" AI-generated code anytime soon. But it's still quite possibly against the terms of this project's AGPL3+ license.
3. Oversight and accountability. AI tools, like any human worker, require a lot of oversight to make sure they're not doing something stupid. The problem is that many people have a tendency to blindly trust what the magic computer genie did for them, which can cause all sorts of problems. Writing code yourself means at least you can be aware of your mistakes sooner and learn from them.
4. Speed isn't the point of the project. If I wanted to get this done quickly, I wouldn't have written the tests, Javadoc, etc. by hand. This program is intended to be as reliable and bug-free as humanly possible, which means that it should be carefully written by humans doing their best to build robust code.
5. It's my project. If you don't like my rules, you are free to clone the project and do just about whatever you want with it as long as you don't break any laws and try to blame me for it.

## What about reviewing pull requests?

Sure, I'd love your help reviewing pull requests! Any and all reviews are welcome, just keep your reviews as positive and constructive as possible.
